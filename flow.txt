HF-SELAP - FILE DEPENDENCIES AND EXECUTION FLOW
================================================

1. DEPENDENCY GRAPH (an arrow "A -> B" means "A imports / uses B")
------------------------------------------------------------------

  hfselap/ascon.py           (no internal dependencies; pure ASCON v1.2)
        ^
  hfselap/primitives.py  ->  ascon.py
        |                    h(), xor(), AeadParams (IV = M^a, AD = M^b, k = M^a xor M^b),
        |                    seal()/open_(), 32-bit timestamps, SimClock, OpMeter
        ^
  hfselap/certificateless.py -> primitives.py (h, METER), cryptography (OpenSSL)
                             KGC, partial keys, validation, SK = x + D, Q, ECDSA sign/verify
  hfselap/config.py          (no internal dependencies)     Config <- config.json
  hfselap/messages.py    ->  primitives.py (field sizes)    Msg1..Msg4, signed inputs,
                                                            inter-TA formats
        ^
  hfselap/entities.py    ->  primitives, messages, certificateless, config, ascon
                             VehicleSmartCard, Vehicle (A-1, A-6),
                             UAVSmartCard, UAV (A-4), session_key, refreshed_tid
        ^
  hfselap/ta.py          ->  entities, messages, primitives, certificateless, config
                             RegionalTA (VR-2, UR-2, A-2, A-3, A-5), NeedRecord
        ^
  hfselap/federation.py  ->  ta (record types), messages, primitives, ascon,
                             certificateless, entities
                             RootTA (+ KGC, trust update), SecureLink
        ^
  hfselap/loadbalancer.py -> config (and RootTA / RegionalTA objects at run time)
                             HealthMonitor, LoadBalancer
        ^
  hfselap/system.py      ->  config, entities, federation, loadbalancer, messages,
                             primitives, certificateless, ta
                             HFSELAP facade (the class every caller uses)
        ^
  hfselap/channel.py     ->  ascon           (data protection after authentication)
  hfselap/simulation.py  ->  system, entities, loadbalancer, messages, primitives, ta
  hfselap/attacks.py     ->  system, config, entities, federation, messages, primitives,
                             certificateless

  Top-level users:
  demo.py                 -> hfselap (system, attacks, channel), config.json
  tests/*.py              -> hfselap modules (+ PyPI "ascon" for cross-checking)
  experiments/common.py   -> hfselap, matplotlib, config.json
  experiments/exp_*.py    -> common.py + hfselap
  experiments/run_all.py  -> every exp_*.py, writes results/*.json + results/figures/*.png
  report/diagrams.py      -> matplotlib only (architecture + message-flow figures)
  report/build_report.py  -> results/*.json, results/figures/*.png, diagrams.py, python-docx
                             -> HF-SELAP_Report.docx

  Data files:
  config.json             read by Config.load (demo, experiments, tests)
  results/*.json          written by experiments, read by build_report.py


2. SET-UP FLOW (what happens when a federation is built)
--------------------------------------------------------

  HFSELAP(cfg)                      system.py
    -> RootTA(cfg, clock)           federation.py   root key, KGC (s, P_pub = sG), registries
    -> HealthMonitor, LoadBalancer  loadbalancer.py

  HFSELAP.add_ta("RTA-1", region)
    -> RegionalTA(...)              ta.py           private master key k_TA
    -> RootTA.add_ta(ta)            federation.py   new ASCON link key (SecureLink)

  HFSELAP.trust(a, b, value)        -> RootTA.set_trust      inter-TA trust matrix

  HFSELAP.register_vehicle(name, region)              (secure enrolment channel)
    VR-1  vehicle: N_VR1, PID_V = h(ID_V || N_VR1), secret value x_V, X_V = x_V*G
    VR-2  RegionalTA.register_vehicle(PID_V, X_V): TID_V, N_VR2,
          M_VR1 = PID_V xor h(N_VR2 || k_TA)
          -> RootTA.issue_partial_key (KGC): R_V, D_V = r_V + h_V*s
          Q_V = X_V + R_V + h_V*P_pub; record <TID_o=None, TID_c, N_VR2, M_VR1, Q_V>
          -> RootTA.deposit_vehicle  (sealed escrow copy + TID directory entry)
    VR-3  vehicle: check D_V*G = R_V + h_V*P_pub, SK_V = x_V + D_V
          VehicleSmartCard.issue: M_VR2, ASCON-protected (N_VR1 || N_VR2 || SK_V)

  HFSELAP.register_uav(name, region)
    UR-1  RegionalTA.check_uav_identity; UAV: N_UR1, PID_U = h(ID_U || N_UR1), x_U, X_U
    UR-2  RegionalTA.register_uav: C_U, M_UR1 = PID_U xor h(ID_U || C_U || k_TA),
          partial key (R_U, D_U) from the KGC, Q_U -> RootTA.deposit_uav
    UR-3  UAV: validate D_U, SK_U = x_U + D_U;
          UAVSmartCard.issue: M_UR2, ASCON-protected (N_UR1 || C_U || SK_U)


3. ONE AUTHENTICATION (HFSELAP.authenticate, system.py)
-------------------------------------------------------

  login            Vehicle.login / UAV.login -> smart card decrypts the credentials
                   and the private key SK
  select TA        HFSELAP.select_ta -> LoadBalancer.select: eligible RTAs (up, trusted,
                   L_i <= L_max), Score = w1(1-L) + w2 A + w3 R + w4 D_score, argmax
  A-1  Vehicle.start(ID_U, ID_TA)     sigma_V = Sign(SK_V, TID||N_A1||ID_U||ID_TA||T1)
                                      -> Msg1 {TID, C_A1, Tag_A1, T1}  (1056 bits)
       Channel tap (attacks may drop / modify / replay here)
  A-2  RegionalTA.handle_msg1         freshness, replay cache, TID lookup in
       A-3                            <TID_o, TID_c>, RevCheck, decrypt, Verify sigma_V,
                                      look up UAV record, TID_new = h(TID||N_A2||T1),
                                      build Msg2 (800 bits)
       If a record is missing: NeedRecord -> RegionalTA.fetch -> RootTA.fetch
       (trust + revocation checked; record sent over the ASCON inter-TA link and
       cached), then the handler is simply called again.
  A-4  UAV.respond                    PID_U = h(ID_U||N_UR1), decrypt, SK_HF, SKV,
                                      sigma_U = Sign(SK_U, ...), Msg3 (928 bits)
  A-5  RegionalTA.handle_msg3         decrypt, Verify sigma_U, M_A9, dual-record update
                                      (TID_o <- TID, TID_c <- TID_new), Msg4 (800 bits);
                                      queue the TID update in the outbox
       RegionalTA.flush_federation    -> RootTA.sync_tid (asynchronous): update escrow
                                      + directory, push to the home RTA and to RTAs
                                      holding cached copies; stale updates ignored
  A-6  Vehicle.finish                 decrypt Msg4, SK_VU, check SKV, compute and adopt
                                      TID_new = h(TID || N_A2 || T1)
  result  AuthResult(ok, sk_vehicle == sk_uav, bits per message, serving TA, ...);
          RootTA.observe updates reliability R_i and inter-TA trust
          (X_new = alpha X_old + (1 - alpha) S)
  after   SecureDataChannel(SK) protects emergency data (channel.py)


4. FEDERATION OPERATIONS
------------------------

  Fail-over     RegionalTA.fail() -> monitor reports it down -> LoadBalancer picks
                another trusted RTA -> that RTA fetches delegated credentials.
                RegionalTA.recover() -> RootTA.resync (missed revocations and TID
                updates) -> flush_federation.
  Revocation    HFSELAP.revoke -> RootTA.revoke: versioned registry entry, REVOKE
                message to every operational RTA (apply_revocation purges indexes
                and caches); offline RTAs catch up through resync.
  Recovery      HFSELAP.reenrol_vehicle / reenrol_uav: revoke the old handle, then
                register again (new TID/N_VR2 or C_U, and a new key pair).
                No other entity is touched, so there is no network reset.
  PQ mode       config protocol.pq_mode = true -> AeadParams uses Ascon-80pq with a
                160-bit key; messages and storage keep the same size. (The
                certificateless ECDSA layer is unchanged and is not quantum-safe.)


5. SIMULATION FLOW (simulation.py, used by experiments E5-E7)
-------------------------------------------------------------

  Simulation(system) -> event heap in simulated milliseconds; the system's
  SimClock is set to each event's time, so timestamps and Delta T are checked
  against simulated delays (including queueing).

  submit(t, vehicle, uav) -> _new_request -> _start_attempt
     LoadBalancer.select (or static home routing) -> Vehicle.start (timed)
     -> network hop (latency + jitter, loss) -> _ta_arrival (FIFO queue, capacity,
     "busy" reply on overflow) -> _ta_serve runs handle_msg1 for real, and its
     measured CPU time becomes the service time -> UAV queue -> UAV.respond
     -> TA queue -> handle_msg3 -> flush_federation (CPU time accounted separately)
     -> Vehicle.finish -> request finished; its delay is split into
     T_auth = T_req + T_TA + T_authz + T_UAV + T_resp, and summary() reports the
     load-imbalance metric LI over the RTA utilisations.
  A timeout (1.5 s) triggers a retry on another RTA (up to 3 attempts).
  Heartbeats every 500 ms; an RTA is declared down after 3 missed beats, or
  earlier when a timeout coincides with a missed beat.
  fail_ta / recover_ta inject faults; loss_fn models speed-dependent loss.
